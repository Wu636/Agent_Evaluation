# 训练优化流式超时修复

当训练优化模型持续生成较长的 JSON 方案时，旧实现仍可能在生成中途终止并显示英文 `The operation was aborted due to timeout`。本次修复避免把正常的慢速输出当成单次超时，并保留部署平台的总执行上限。

## 问题依据

2026 年 11 月 24 日的 Chrome Network 记录显示，`POST /api/training-refine` 返回 `200 OK` 和 `text/event-stream`，首个响应等待约 0.6 秒，整个请求持续约 4 分钟。22:54:50 仍收到“已接收 3,133 字符”的进度，22:54:51 随后收到 `type: error` 的超时事件。这说明连接已建立，失败发生在生成方案期间；HTTP 200 不表示方案已经生成成功。

代码中存在三个相互嵌套的时间限制：

- `callRefiner`：90 秒首字等待，以及无论是否持续输出都会触发的 150 秒单次定时器。
- `generateTrainingRefinementPlan`：覆盖初次生成和压缩重试的 240 秒总定时器。
- 路由：包含源图读取的 285 秒总预算，Vercel 函数配置为 300 秒。

150 秒定时器会丢弃已经生成的正文并重新生成，第二次尝试却不能重新获得 240 秒。外层 `AbortSignal.timeout()` 到期后，`signal.throwIfAborted()` 直接抛出原始 `TimeoutError`，绕过面向用户的模型错误说明。前端执行日志使用 `error || log`，报错后又隐藏了此前的进度。

该线上记录与当前代码中的总超时路径一致；没有服务端调用日志，无法仅凭浏览器记录确认当次是否发生过 150 秒压缩重试。

## 改动与时间边界

- 保留 90 秒首字等待；有正文后改为连续 60 秒没有新正文才取消本次模型请求。持续输出超过 150 秒时继续接收，不因此重试。
- 模型阶段最多使用 270 秒，且不得超过路由传入的绝对截止时间；路由在 285 秒预算内另留 5 秒供生成阶段结束和发送终态。源训练读取耗时不会在进入模型阶段后被清零。
- 仅在至少还有 30 秒预算时发起压缩重试；不足时立即说明剩余时间不足，不承诺一次无法执行的重试。
- 总预算用可清理的定时器和中文 `RefinerRequestError` 结束，说明实际耗时、当前尝试及接收字符数，返回 504 语义和缩小范围的建议。所有成功、失败和取消路径均释放对应定时器。
- 日志同时保留错误和此前进度。只有完整生成并通过图谱校验的方案可以作为成功结果，部分 JSON 不会被当作成功方案返回或注入。

## 验证

在 `frontend` 目录运行：

```sh
node --test lib/training-refiner/engine.test.mjs
node node_modules/typescript/bin/tsc --noEmit --incremental false
```

回归用例使用内存中的模拟时钟与模拟模型数据流，覆盖持续输出超过 150 秒、首字和空闲超时、总预算到期、调用方更早截止、调用方不能延长本地预算、剩余时间不足不重试、源图耗时计入预算，以及 JSON 超时响应状态。禁止测试访问真实网络或执行平台注入。

## 部署与限制

本次不提高 Vercel 的 300 秒函数配置，也不修改训练卡片的最大交互轮次。部署新版本后修复才会对线上生效。模型或网关自身的更短超时仍可能导致失败，超长方案也仍受总预算约束；需要超过单次函数时限的任务，应另行采用可持久化的分批任务和断点恢复，不能靠 SSE 心跳无限延长执行时间。
