两次都已经收到网关返回的错误响应，并非本地等待到期。增加本地超时时间不会改变这两次收到的 500/503。网关响应证明故障发生在这条请求链路中；它没有给出更深层的失败原因，仍需服务方结合 requestId 查询。

`POST /api/training-generate 200` 是流式响应连接的状态。生成中的错误通过 SSE 事件返回，不能据此判断生成成功。

## 使用实际流式代码的对照

通过仓库的 `callLLMStream` 实际读取完成帧，使用服务端配置，输出额度为 8000。长输入是 22801 字符的合成教学记录，仅要求回复 `OK`，并非用户正式教师文档，也未验证完整 17 阶段生成。

| 模型 | 用户输入字符数 | 收到响应头 | 结束原因 | 正文 | 总耗时 |
| --- | ---: | --- | --- | ---: | ---: |
| claude-opus-5 | 3 | HTTP 200，3124 ms | stop | 2 字符 | 3886 ms |
| claude-opus-5 | 22801 | HTTP 200，2358 ms | content_filter | 0 字符 | 2359 ms |
| claude-opus-4.8 | 22801 | HTTP 200，2655 ms | stop | 2 字符 | 2657 ms |

短请求成功只证明该次请求可用。长样本的 `content_filter` 是另一种上游响应，尚无证据将其等同于正式请求的 503，也没有证据说明 22801 字符超过模型上下文窗口。

网关模型目录包含 `claude-opus-5`，调用时模型 ID 保持原值。此前将平台 Claude 请求统一为 `maxTokens` 后，短请求曾成功，但正式请求仍失败，因此“额度字段已经解决根因”的判断证据不足。

## 本地修正及验证

- 区分 HTTP 错误与 HTTP 200 下的 `content_filter`、`refusal`、空正文。
- `content_filter` / `refusal` 不进入训练生成的自动续写重试。
- 空正文按可重试输出异常处理；首轮最多重试一次，失败后报告错误，不以空内容开始 12 轮续写。
- 保留 HTTP 状态和网关 requestId；通道异常提示不再暗示已确认是参数兼容性问题。
- 新增路由和流式解析回归用例；相关 132 项测试、TypeScript 类型检查通过。

这些修正解决本地误判和重复续写，不代表网关 Opus 5 通道已恢复。

## 服务方核查所需信息

请服务方按上方两条 requestId 查询 Opus 5 实际路由、上游错误正文及模型通道的参数支持情况；另行确认 `content_filter` 是哪个环节返回、具体判定原因。若需要复现正式生成，须使用同一份教师文档、模块规划及系统提示；等长合成文本只能作为对照。
